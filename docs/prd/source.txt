1. Overview
Dowser is a four-person Cal Hacks 13.0 build (Climate track, software + hardware, Oct 23–25, 2026, Palace of Fine Arts, SF) that finds undocumented orphaned oil and gas wells on century-old USGS maps, ranks them for plugging crews, and confirms leaks in the field with a handheld methane sensor. The deliverable by Sunday 9 AM is a working end-to-end demo: historical map tile in, ranked candidate wells out, sensor reading in the field, live map updated.

1.1 One-liner
A computer vision model finds oil and gas well symbols on historical USGS topographic maps, flags the ones missing from state records, and ranks them for plugging crews, who confirm leaks with a cheap handheld methane sensor that logs readings back to a live map.

1.2 Problem
There are likely hundreds of thousands of undocumented orphaned oil and gas wells in the US (estimate from the proposal; cite a source in the Devpost before using a number).

Many leak methane, which is far more potent than CO₂ over the near term. Some sit near homes and schools.

Plugging funding exists, but crews cannot plug wells nobody knows about.

The evidence is already on historical topographic maps, which marked wells with small symbols decades before modern record-keeping. Nobody has the time to scan those maps by hand.

1.3 Why now
The 2021 Infrastructure Act funded orphaned well plugging and states are building out programs. Verify current program status before pitching.

Berkeley Lab and partners have published research showing deep learning can find undocumented wells on historical maps, so the approach is proven. Dowser's differentiator is the end-to-end workflow: detection → records cross-check → ranking → field verification.

USGS has digitized and georeferenced its historical map collection (TopoView), so the raw data is free and ready.

3. Scope
The MVP is one region, one detector, one cross-check, one ranking, one handheld, one live map; anything else waits until the MVP works end-to-end. The stretch gate is Saturday around 6 PM.

3.1 MVP (must ship by Sun 9 AM)
Map ingestion for one region with heavy historical drilling (LA Basin or Kern County, CA): georeferenced historical maps from USGS TopoView, tiled.

YOLO well-symbol detector fine-tuned on a few hundred hand-labeled symbols (Roboflow), with pixel-to-lat/long conversion using each map's georeferencing.

Records cross-check against CalGEM: any detection with no documented well within about 100 m becomes a candidate undocumented well.

Ranking by proximity to homes and schools (OpenStreetMap), map confidence and field confirmation.

Claude agent writing a plain-English brief per candidate.

Handheld verifier: ESP32 + MQ-4 methane sensor + small OLED display, posting readings to Convex.

Live map UI (Next.js + MapLibre) with old map / satellite toggle, documented vs. undocumented wells, and live sensor readings.

A scripted 3-minute demo, a backup demo video and a Devpost submission.

3.2 Stretch (only if the MVP works end-to-end by Saturday ~6 PM)
Claude vision as a second-pass verifier on uncertain detections.

A second region or state.

Overlay of satellite methane data where available.

3.3 Out of scope
User accounts, authentication and multi-tenant data.

Mobile app (a simple phone web page for location is allowed, see risks).

Real methane handling or any real gas release.

Regulatory-grade calibration or compliance reporting.

Writing project code before the event starts (gathering data and parts is allowed; writing project code early is not).

5. System architecture and data
Dowser is a one-way pipeline from old maps to a ranked list, with Convex as the single live store that the handheld writes into and the map reads from.

The pipeline row runs when a tile loads; sensor readings and map updates both go through Convex, so the demo needs no manual refresh.

5.3 Interfaces (proposed)
Reading ingest: a Convex HTTP action the ESP32 posts to (JSON: deviceId, ts, raw, corrected, wellId or lat/lon). Use an HTTPS client on the device; note any certificate shortcut you take for the demo.

Tile upload: UI control or CLI that stores the tile and starts the detection workflow.

Live queries: the map subscribes to candidates, documentedWells and readings; the ranked list is a query sorted by score.

Brief generation: a server function that sends a candidate's JSON to Claude and stores the text.

5.4 Geospatial rules
Compute distances in a projected, meter-based coordinate system (for example California Albers, EPSG:3310), not in degrees; store WGS84 lat/lon for display.

The pixel-to-geo step uses each tile's own transform; never reuse one sheet's transform for another sheet.

Map-era differences matter: record each tile's year and report detector results per era.

Cross-check radius (~100 m), proximity radius and score weights are config values, not constants buried in code.

6.3 Factory Droid SDK: design to the prize criteria
Prize rule (Best Use of the Factory Droid SDK): the project must use the Droid SDK (TypeScript or Python) meaningfully, Droid must do real work in the running product and not only help write code, and the README must explain where and how Droid is used. It scores well when Droid runs on a trigger you designed, you control what it can touch with safety built in, and its work is visible (plans, steps, diffs, results). It scores poorly as a chatbot wrapper, a slides-only demo, or when nobody can tell what the agent did.

Design: Droid is the spatial triage agent. It is not a chat box and not the Claude brief writer; the Claude agent writes briefs, Droid decides which detections become candidates and what changed.

7.3 Honesty and accuracy rules
Report precision and recall only on maps we actually checked, and say which maps and eras.

Call detections "candidate undocumented wells", never "found wells", unless verified against records.

7.4 What you may be missing
Time already used. It is Friday afternoon, so the pre-event checklist items (burn-in, ordering, pre-labeling) are mostly gone. Plan for a short sensor warm-up at the venue and treat the hardware as the riskiest path.

Rules check. Ask at check-in what is allowed on pre-existing data, pretrained models, open-source code and pre-written code. The proposal's rule is that gathering data is fine and writing project code early is not.

Judge flow. Judges often visit tables for a few minutes and may come in waves. Prepare a 60-second version, the 3-minute version and a self-running loop.

8.3 Demo plan (3 minutes)
0:00–0:30, problem. Orphaned wells leak methane and crews cannot plug wells nobody knows about. The evidence is on century-old maps.

0:30–1:15, detection. Upload a historical tile; detections appear; undocumented candidates turn a distinct color on the map.

1:15–1:45, ranking. Open the ranked list; click the top candidate; show the school-distance score and the Claude brief.

1:45–2:30, field check. "Walk" to the candidate with the handheld near the simulated leak; the reading appears; the candidate turns red and jumps to rank 1.

2:30–3:00, impact and ask. The region's N candidates and M near homes or schools (labeled as candidates); who it helps; what comes next.

Rules for the demo: show the "simulated" banner, state the detector's measured precision and recall, and keep a backup video and replay mode ready before every judging round.

8.4 Making the demo work at the venue
Network first. Test the ESP32 on a phone hotspot or travel router as soon as it works on anything. Do not assume venue Wi-Fi will let a microcontroller join.

Pre-seed the demo state. Load tiles, detections, candidates and briefs into Convex before judging, so the live part is only the upload and the sensor.

Two ways to trigger the leak. The physical simulated leak (if approved) and a software button that posts the same reading.

Run mode switch. One config flag for live detector vs. ground truth, and live sensor vs. replay.

Self-running loop. A looping screen recording or auto-play demo mode for when nobody is free to present.

Rehearse three times with someone who has not seen it, and time each run.
